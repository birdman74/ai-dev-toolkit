# New Project Setup Checklist

Use this checklist when wiring a new project to the ai-dev-toolkit persona workflow.
This reflects lessons learned from the StreamVault project - follow it exactly to avoid
the pitfalls documented in DEVLOG.md.

---

## 1. GitHub Repository

- [ ] Create repo on GitHub (public for portfolio projects)
- [ ] Set default branch to `main` - do this in GitHub account Settings → Repositories BEFORE creating the repo
- [ ] Add All Rights Reserved `LICENSE` file (or MIT if open source)
- [ ] Add `.gitignore` covering secrets, build artifacts, OS files, IDE files
- [ ] Add `.env.example` documenting all required environment variables (no real values)
- [ ] Add `.gitattributes` normalizing line endings to LF:
```
* text=auto eol=lf
*.bat text eol=crlf
*.cmd text eol=crlf
```
- [ ] Set remote URL to SSH format - never HTTPS:
```bash
git remote set-url origin git@github.com:<your-github-username>/<repo>.git
```

**Why SSH remote matters**: persona containers authenticate via `GIT_SSH_COMMAND` using a deploy key. If the remote is HTTPS, pushes from persona containers will fail silently or require credential workarounds.

## 2. SSH Deploy Key (one per project, shared across all personas)

```bash
mkdir -p /home/brian/.claude/git-identities/<project>
ssh-keygen -t ed25519 -C "claude-<project>" \
  -f /home/brian/.claude/git-identities/<project>/id_ed25519
# Leave passphrase EMPTY - containers run non-interactively
ssh-keyscan github.com > /home/brian/.claude/git-identities/<project>/known_hosts
```

Register the public key in GitHub:
- Repo → **Settings → Deploy keys → Add deploy key**
- Title: `claude-<project>-personas`
- Key: paste contents of `id_ed25519.pub`
- Allow write access: ✅

Verify:
```bash
ssh -i /home/brian/.claude/git-identities/<project>/id_ed25519 \
    -o IdentitiesOnly=yes \
    -o UserKnownHostsFile=/home/brian/.claude/git-identities/<project>/known_hosts \
    git@github.com
```
Expected: `Hi birdman74/<repo>! You've successfully authenticated...`

## 3. GitHub Bot Account (for PR automation)

The bot account (`briankcampbell-streamvault-bot`) can be reused across projects.

- [ ] Add bot account as collaborator on the new repo: Repo → **Settings → Collaborators → Add people** → `briankcampbell-streamvault-bot` → Write role
- [ ] Bot must accept the collaborator invitation (check `brian.k.campbell+streamvault-bot@outlook.com`)

### Token 1: Bot Account PAT (for the pipeline's bot operations)

Generate from the bot account (log in as bot in incognito):
- **Settings -> Developer settings -> Personal access tokens -> Tokens (classic) -> Generate new token**
- A **classic** token is required: fine-grained tokens from a collaborator account cannot access repositories the account does not own, even with every permission enabled.
- Note: `<project>-pipeline`
- Expiration: 90 days (set a calendar reminder to rotate)
- Scopes: `repo`

Add it as a GitHub Actions secret (never as an environment variable named `GITHUB_TOKEN`, which Actions reserves):
- **Settings -> Secrets and variables -> Actions -> New repository secret**
- Name: `<PROJECT>_BOT_GH_TOKEN`
- Value: paste token

The workflows use it to read PRs and verdict comments and to create, update and close `needs-brian` escalation issues. Escalations must come from the bot, not from your account: GitHub never notifies you about your own activity.

The personas themselves do **not** receive this token. Their `gh` sessions log in as the bot through the mounted gh config directory (see Persist gh CLI Auth below); `gh` only reads `GH_TOKEN`/`GITHUB_TOKEN` from the environment, so passing a project-named variable into the containers does nothing.

---

### Token 2: Queue Manager PAT (for issue label operations in GitHub Actions)

Generate from YOUR account (the repo owner, not the bot):
- **Settings -> Developer settings -> Fine-grained personal access tokens -> Generate new token**
- Token name: `<project>-queue-manager`
- Expiration: 90 days (set a calendar reminder to rotate)
- Resource owner: your account (the repo owner)
- Repository access: Only select repositories -> select your project repo
- Permissions:
  - Issues: Read and write
  - Metadata: Read (auto-selected)

Unlike the bot token this one is **not** project-prefixed: the workflow templates in `workflows/` reference `secrets.QUEUE_MANAGER_GH_TOKEN` verbatim.

Add as a GitHub Actions secret in the repo:
- **Settings -> Secrets and variables -> Actions -> New repository secret**
- Name: `QUEUE_MANAGER_GH_TOKEN`
- Value: paste token

This token is used only by the queue (the `test-kickoff` gate in `pipeline-main-and-merge.yml`, via `scripts/transition.sh`) and `sync-blocked-labels.yml`, for adding/removing the `in-progress` and `blocked` labels and closing completed story issues. It must be generated by the repo owner because fine-grained PATs from collaborator accounts cannot perform write operations on repos they do not own.

### Token 3: Project Board PAT (for the board sync)

Generate from YOUR account (the board owner):
- **Settings -> Developer settings -> Personal access tokens -> Tokens (classic) -> Generate new token**
- A **classic** token is required: `GITHUB_TOKEN` and fine-grained tokens cannot reach a user-owned Projects V2 board (the board lookup silently finds nothing).
- Note: `<project>-project-board`
- Scopes: `project`, `repo`

Add as a GitHub Actions secret named `PROJECT_BOARD_GH_TOKEN`. Used only by `sync-project-board.yml`. The board title, Status field and column names it uses are set in `.github/pipeline-config.env`.

### Persist gh CLI Auth Inside Containers

```bash
mkdir -p /home/brian/.config/gh-<project>
```

After first `gh auth login` inside a persona container (requires browser device code flow logged in as bot account), copy the config out before the container exits:

```bash
docker cp <container-id>:/home/brian/.config/gh/hosts.yml \
  /home/brian/.config/gh-<project>/hosts.yml
```

Add the `workflow` OAuth scope (required to push `.github/workflows/` files):
```
!gh auth refresh -h github.com -s workflow
```
Complete browser authorization as the bot account. This is persisted in the mounted config.

Mount in compose files:
```yaml
- /home/brian/.config/gh-<project>:/home/brian/.config/gh
```

## 4. Project Context Files (CLAUDE.md, CONTRIBUTING.md, ADRs)

### Persona CLAUDE.md files

```bash
mkdir -p .claude/personas/po .claude/personas/dev .claude/personas/test
```

- Copy `personas/templates/po/CLAUDE.md` → `.claude/personas/po/CLAUDE.md`
- Copy `personas/templates/dev/CLAUDE.md` → `.claude/personas/dev/CLAUDE.md`
- Copy `personas/templates/test/CLAUDE.md` → `.claude/personas/test/CLAUDE.md`
- Replace all `<REPLACE:...>` placeholders in each:
  - `<REPLACE:project-name>` - the project name
  - `<REPLACE:reviewer-name>` - the human architect/reviewer (CODEOWNER)
  - `<REPLACE:verify-command>` (Dev, Test) - the full-suite command, e.g. `mvn clean verify`
  - `<REPLACE:stack-summary>` (Dev) - the backend stack, e.g. `Java 25, Spring Boot 3.5.x, Spring AI`
- The Dev and Test templates instruct the personas to consult `docs/adr/` for
  the project's testing-pattern decision before writing cross-cutting tests.
  Seed at least one ADR there (see below) so that instruction resolves.

### Root CLAUDE.md

- Create `CLAUDE.md` at repo root with project-wide context: stack, coding
  conventions, git workflow, per-persona git identities, and the STATUS.md
  update protocol.
- Every persona container loads this file next to its own persona `CLAUDE.md`,
  so anything it says about the workflow must match the persona files exactly
  (Test goes first, then Dev's design review, then implementation). A stale
  overview here contradicts the personas on every run. Keep it to a short
  overview and leave the details to the persona files.
- List only tools the project actually uses in its stack table; record
  planned-but-unused tools as deferred, with a backlog entry saying what would
  trigger them.

### CONTRIBUTING.md

- Copy `templates/CONTRIBUTING.md` → `CONTRIBUTING.md` and replace the
  `<REPLACE:...>` placeholders.
- This is the canonical home for coding and testing conventions. Keep the
  persona templates pointing at it rather than duplicating standards.

### ADR directory

```bash
mkdir -p docs/adr
```

- Copy `templates/adr/ADR-NNN-title.md` as the skeleton for each new ADR.
- Create ADRs when a non-obvious decision is made that future stories must
  follow (testing patterns, security config, schema conventions). The Dev and
  Test personas are instructed to consult `docs/adr/` before inventing a
  pattern and to escalate to the human when a decision is not covered.

## 5. Docker Images and Compose Files

### Dockerfile placeholders (set before `docker build`)

The three Dockerfiles carry two placeholders that must be replaced before the
images are built. **The same values must then be used in the compose file** -
the image and the compose file have to agree or the bind mounts and in-container
paths will not line up.

| Placeholder | Represents | Where it appears | Value to use |
|---|---|---|---|
| `<REPLACE:home-dir>` | The absolute path of the home directory of the host user who runs the persona containers. It is baked in as the container's `HOME` **and** used verbatim as the host side of the `.claude` / `.claude.json` bind mounts, so the container's home path is made to mirror the host's - `~/.claude` then resolves to the same place inside and outside the container. | All 3 Dockerfiles: `mkdir -p`, `chown`, `ENV HOME`. `compose/claude-persona.yml`: `HOME=`, both paths in `GIT_SSH_COMMAND`, and the `.claude` / `.claude.json` / persona-`CLAUDE.md` volume entries (both sides). | The Linux home directory of the user running the containers, e.g. `/home/brian` (on WSL2/Ubuntu). Must be a real, readable directory on the host that already contains `.claude/`, `.claude.json`, and `.claude/git-identities/<project>/` from steps 2–4. |
| `<REPLACE:workspace-name>` | The in-container project root. | All 3 Dockerfiles: `WORKDIR /<REPLACE:workspace-name>`. `compose/claude-persona.yml`: the container side of the project bind mount. | The project name, e.g. `streamvault` (mounts the repo at `/streamvault`). |

Build the images with the placeholders filled in - see the build commands in
the repo README (`claude-base-img`, then `claude-po-img` and `claude-dev-img`).

### Compose files

For each persona (po, dev, test), copy `compose/claude-persona.yml` to:
```
/mnt/e/docker/claude-<project>-<persona>/docker-compose.yml
```

Replace all `<REPLACE:...>` placeholders. Key fields:
- `image`: use `claude-po-img` for PO, `claude-dev-img` for Dev and Test
- `<REPLACE:home-dir>` / `<REPLACE:workspace-name>`: use the **exact same
  values** baked into the image above
- `GIT_SSH_COMMAND`: point to `<REPLACE:home-dir>/.claude/git-identities/<project>/id_ed25519`
- `<REPLACE:your-email>` / `<REPLACE:email-domain>`: the local-part and domain of
  your git address - commits are attributed to
  `<your-email>+claude-<project>-<persona>@<email-domain>`
- No token environment variable: `gh` inside the container logs in from the mounted gh config
- volumes: mount `.claude`, `.claude.json`, persona CLAUDE.md, project workspace
  (at `/<REPLACE:workspace-name>`), and gh config

Throughout this document, example paths written as `/home/brian/...` are this
same `<REPLACE:home-dir>` directory.

## 6. Launcher Scripts

For each persona (po, dev, test), copy `scripts/launch-persona.sh` to:
```
~/bin/<project>-<persona>.sh
```

Replace all `<REPLACE:...>` placeholders. Make executable:
```bash
chmod +x ~/bin/<project>-po.sh
chmod +x ~/bin/<project>-dev.sh
chmod +x ~/bin/<project>-test.sh
```

`--dangerously-skip-permissions` handling differs between the two templates:
- `launch-persona.sh` (interactive) ships with the flag **commented out**
  behind a warning. Only uncomment it once container sandboxing is set up and
  the persona's mount scope is limited and reviewed.
- `launch-persona-auto.sh` (used by GitHub Actions) ships with the flag
  **active** - automation cannot answer interactive approval prompts.

`launch-persona-auto.sh` also gives every run its own container name (the
workflow sets `PERSONA_CONTAINER_NAME`; otherwise a unique one is generated)
and removes the container when it exits or is interrupted, so a run that
times out never blocks the next one or collides with an interactive session.

When enabled, the flag lets personas run without per-command approval. The
blast radius is contained by:
- Scoped filesystem mounts (workspace only)
- Scoped GitHub permissions (bot account, no merge capability)
- Branch protection on main requiring PRs

## 7. Pipeline Scripts

Copy every script from the toolkit's `scripts/` into the project's `scripts/` (the launcher templates are the exception: they go to `~/bin`, section 6):

```bash
mkdir -p scripts
cp <toolkit>/scripts/{transition,pipeline-config,persona-outcome-check,escalate-to-brian,check-prerequisites,sync-blocked-labels,sync-project-board}.sh scripts/
cp <toolkit>/scripts/next-story-template.sh scripts/next-story.sh
```

They need no edits: everything project-specific comes from `.github/pipeline-config.env` (next section) and the `GH_REPO` the workflows pass in. The workflows `chmod +x` them before use.

| Script | Role |
|---|---|
| `transition.sh` | The registry of hand-offs: routing, live state checks, round limits, prompts, expected outcomes |
| `pipeline-config.sh` | Reads and validates `.github/pipeline-config.env` |
| `persona-outcome-check.sh` | GitHub checks used to verify each persona's result |
| `escalate-to-brian.sh` | Opens, updates and auto-closes `needs-brian` issues |
| `next-story.sh` | The queue: lowest-numbered open story whose prerequisites were all closed as completed; one story `in-progress` at a time; fails closed on API errors |
| `check-prerequisites.sh` | The single rule for "is this story unblocked?" |
| `sync-blocked-labels.sh`, `sync-project-board.sh` | Keep `blocked` labels and the project board in step with story state |

If you change a prompt or an expected outcome, change it in `transition.sh`; if you change a persona's hand-off file names, change them in both `transition.sh` and the persona `CLAUDE.md`.

## 8. Pipeline Config and GitHub Actions Workflows

### Config

```bash
cp <toolkit>/templates/pipeline-config.env .github/pipeline-config.env
```

Fill in every `<REPLACE:...>` value: your login (`OWNER_LOGIN`, `ESCALATION_ASSIGNEE`), the bot login (`BOT_LOGIN`), the three persona git author names (must match `GIT_AUTHOR_NAME` in the compose files), `VERIFY_COMMAND` (your full-suite command, e.g. `mvn clean verify`), the three `-auto.sh` launcher paths, and the project board's title and column names. The round limits and timings have working defaults. `scripts/pipeline-config.sh` rejects unknown, missing or duplicate keys, non-numeric limits, relative paths, and a persona timeout above 330 minutes, so a typo stops the pipeline loudly instead of misbehaving.

### Workflows

Copy every file from `workflows/` into the project's `.github/workflows/`:

```bash
mkdir -p .github/workflows
cp <toolkit>/workflows/*.yml .github/workflows/
```

Then replace the few `<REPLACE:...>` placeholders, listed in each file's header:
- `<REPLACE:github-username>/<REPLACE:repo-name>` in the `uses:` line of every `pipeline-*.yml` adapter. It must name your repository at `@main`: the adapters call the reusable `persona-run.yml` from `main`, so pipeline fixes reach in-flight stories without merging `main` into their branches. GitHub does not allow expressions in `uses:`, so this cannot come from the config.
- `<REPLACE:bot-gh-token-secret-name>`: the Actions secret holding the bot PAT (section 3).
- `<REPLACE:java-version>` / `<REPLACE:node-version>` in `ci.yml`.

Accounts, author names, limits and timings are **not** in the workflows: they come from `.github/pipeline-config.env`. Job-level `if:` conditions only pre-filter on account-free facts (a review state, a verdict marker); every account check runs in the gate job.

Gate jobs and the sync workflows run on `ubuntu-latest`; `persona-run.yml` runs on your `self-hosted` runner. Every workflow ships with an explicit least-privilege `permissions:` block and passes untrusted event fields through `env:`. Leave both in place.

## 9. Branch Protection

First add `.github/CODEOWNERS` with a single line so the "require code owner
review" rule has an owner to route to:
```
* @<your-github-username>
```
The bot account is deliberately **not** a code owner - bot (Test) approval and
human approval are independent requirements.

Then, in GitHub repo → **Settings → Rules → Rulesets → Add ruleset**:
- Target: `main`
- Bypass list: add `birdman74` (for direct STATUS.md commits)
- Rules to enable:
  - Restrict deletions ✅
  - Require a pull request before merging ✅
    - Require review from Code Owners ✅
  - Require status checks to pass ✅ - the `ci.yml` jobs are
    `Validate Repository Structure`, `Backend Build`, `Frontend Build`
  - Block force pushes ✅

## 11. Verify Everything Works

```bash
# Test PO persona
<project>-po.sh
# Inside: verify CLAUDE.md loaded, workspace correct, git identity set
/status
exit

# Test Dev persona
<project>-dev.sh
# Inside: verify tools
!java -version      # should show Java 25
!mvn -version       # should show Maven 3.9.16
!gh auth status     # should show bot account authenticated
!ssh -T git@github.com  # should authenticate via deploy key
exit
```

Then verify the pipeline itself, from the project root:

```bash
# 1. The config parses and every value is valid (prints every key, exits 0)
bash scripts/pipeline-config.sh

# 2. Each automated launcher runs headless and cleans up its container
#    (prints ok, exit=0, and docker ps lists nothing)
~/bin/<project>-po-auto.sh "Reply with the single word ok and do nothing else."; echo "exit=$?"; docker ps -a --filter name=claude-<project>-po
```

3. Push a commit of your own to a throwaway `feature/story-000-pipeline-check` branch. In Actions, **Pipeline - Feature Branch Push** should run green with `SKIP: head commit by <you>, not a persona`, and its persona job should be skipped. That proves the gate runs from `main`, reads the config, and reaches the API with the bot token. Delete the branch afterwards.
4. Run **Sync Project Board Status** with the issue number blank and **Dry run** checked. It should list every story issue with OK, MOVE or ADD and end with 0 failures, which proves `PROJECT_BOARD_GH_TOKEN` and the board names in the config.
5. Run **Sync Blocked Labels** with **Dry run** checked. It should end with 0 failures, which proves `QUEUE_MANAGER_GH_TOKEN`.

## Known Gotchas (learned from StreamVault)

| Gotcha | Fix |
|---|---|
| `GITHUB_TOKEN` reserved by Actions | Use `<PROJECT>_BOT_GH_TOKEN` instead |
| Fine-grained bot PAT cannot reach the repo | Collaborator accounts need a classic token |
| Board sync silently does nothing | `GITHUB_TOKEN` cannot reach a user-owned board; use a classic `PROJECT_BOARD_GH_TOKEN` |
| `The "<X>" variable is not set` warning from Docker Compose | Remove the variable from the compose file: personas authenticate `gh` from the mounted config |
| A timed-out persona left its container running | Use the current `launch-persona-auto.sh` (unique container name, removed on exit) |
| A fix on `main` did not reach an in-flight story | Push workflows run from the pushed branch; keep the adapters' `uses: ...persona-run.yml@main` line and merge `main` into open feature branches after changing an adapter |
| Maven 3.9.9 does not exist | Use 3.9.16 (latest stable) |
| `gh` auth lost on container restart | Mount `/home/brian/.config/gh-<project>` as volume |
| `workflow` scope missing | Run `gh auth refresh -s workflow` inside container as bot |
| Remote set to HTTPS | Always use SSH remote: `git@github.com:birdman74/<repo>.git` |
| `container_name` ignored by `docker compose run` | Use container ID for `docker cp` operations |
| Branch is `master` not `main` | Set account default in GitHub Settings before creating repo |
| STATUS.md committed to feature branch | Always `git checkout main && git pull origin main` before editing STATUS.md |
